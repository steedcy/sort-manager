## 4. MySQL 自动联调与管理员恢复

### 4.1 自动连接检查

根据用户要求，系统自动检查了：

- `MySQL80` 服务状态。
- 无密码 root 登录。
- README 旧默认密码登录。
- `mysql_config_editor` 登录路径。
- MySQL Workbench 本地连接记录。

检查结果是服务运行正常，但没有可复用的有效凭据。系统没有在未授权情况下重置密码，而是请求用户明确授权。

### 4.2 root 密码重置

用户明确授权后，执行了本机 MySQL 管理员恢复流程：

1. 短暂停止 `MySQL80`。
2. 以本机权限恢复模式启动 MySQL。
3. 重置 root 密码。
4. 终止恢复进程并恢复正常服务。
5. 通过 TCP 验证 root 登录。

第一次恢复探针因为 PowerShell 将 MySQL stderr 警告解释为异常而中止。此时密码尚未修改，保护逻辑成功恢复了正常 MySQL 服务。调整原生命令错误处理后，第二次恢复成功。

真实密码仅保存在 Git 忽略的本机文件中，并通过 ACL 限制为当前 Windows 用户访问。

`start.bat` 和 README 同步采用可执行 JAR 方式。

## 6. v1.2 项目进度评估

v1.2 被评估为可正常使用的个人物品管理 MVP：

- 核心业务完成度约 85%。
- 前后端工程质量约 65%。
- 安全与生产准备约 40%。
- 综合完成度约 70%。

主要缺口：

- 没有登录、鉴权和权限隔离。
- CORS 接受任意来源。
- 没有数据库迁移工具，依赖 `ddl-auto=update`。
- 前端依赖存在高危公告。
- 没有浏览器 E2E。
- 仪表盘和分类统计存在 N+1 或全量加载问题。
- 批量操作由前端发起多次单条请求，不具备事务原子性。
- `Items.jsx`、`index.css`、`ItemService.java` 开始偏大。
- 缺少正式部署、备份恢复和监控方案。

由此确定 v1.3 应优先解决安全与可靠性，而不是继续扩展业务功能。

## 7. v1.3 安全与可靠性升级

### 7.1 版本设计

v1.3 选择“最小安全闭环”方案，范围包括：

- 修复前端依赖漏洞。
- CORS 环境变量白名单。
- Flyway 数据库迁移。
- Hibernate `validate`。
- Playwright 真实全栈测试。
- GitHub Actions MySQL E2E。
- 稳定的本地构建和启动配置。

明确不纳入 v1.3：

- 登录和用户体系。
- 多家庭数据隔离。
- 小程序。
- 导入导出。
- Docker Compose。
- 大规模 UI 重构。

### 7.2 前端依赖安全

升级后的主要版本：

- Axios 1.18。
- React Router 7.18。
- Vite 7.3。
- React 插件 5.1。
- PWA 插件 1.3。
- esbuild 0.28。

选择 Vite 7 而不是直接升级 Vite 8，是因为 Vite 7 已脱离已知漏洞区间，并与当前 Node、Tailwind 和 React 插件组合通过依赖解析；Vite 8 当时存在可选 peer 依赖冲突和更高迁移风险。

最终 `npm audit` 从 13 个漏洞、8 个 high 降为 0。

### 7.3 CORS 加固

原配置使用通配来源。v1.3 改为：

- `APP_CORS_ALLOWED_ORIGINS` 逗号分隔白名单。
- 默认仅允许 `localhost:5173` 和 `127.0.0.1:5173`。
- 显式拒绝 `*` 配置。
- MockMvc 测试验证合法来源和未知来源。

### 7.4 Flyway 数据库迁移

新增：

- `V1__create_core_schema.sql`：全新数据库基础结构。
- `V2__add_constraints_and_indexes.sql`：分类名称唯一索引及物品日期索引。

迁移策略：

- 空数据库执行 V1、V2。
- 已有非空 v1.2 数据库 baseline 为版本 1，再执行 V2。
- Hibernate 默认由 `update` 改为 `validate`。
- H2 常规业务测试禁用自动 Flyway。
- 单独的 Flyway 测试覆盖空库和已有非空库模拟升级。

首次实库接管前已创建本机备份，并检查分类重名和现有索引。

实库升级后：

- Flyway baseline 1 成功。
- V2 成功。
- 分类、位置、物品仍为 10/10/6。

### 7.5 示例数据脚本编码事件

Flyway 接管成功后，验证可选示例数据脚本时，PowerShell 管道将 UTF-8 中文转换为本机编码，导致脚本产生错误示例行。

处置过程：

1. 立即停止继续执行。
2. 根据迁移前备份和 ID/时间范围识别新增行。
3. 在事务中删除错误新增的示例行。
4. 核对数据恢复为 10/10/6。
5. 将 README 命令改为 MySQL 客户端直接读取 UTF-8 文件，并显式设置 `--default-character-set=utf8mb4`。
6. 连续执行示例脚本两次，确认数据仍保持 10/10/6。

该事件没有造成原始业务数据丢失。

## 10. 目标技术架构

建议保留统一后端，不为 PC 和小程序分别实现业务服务：

```text
PC Web / React -----------+
                         |
手机小程序 ---------------+--> Spring Boot / API v1
                                      |
                                      +--> 认证与家庭权限
                                      +--> 物品/分类/位置/批量操作
                                      +--> 统计看板
                                      +--> Excel/CSV 导入
                                      +--> 图片存储
                                      |
                                      +--> MySQL + Flyway
```

建议新增的数据模型：

- `user`：用户身份、昵称、密码摘要和状态。
- `household`：家庭数据空间。
- `household_member`：家庭成员和 OWNER/MEMBER 角色。
- `refresh_token`：可撤销、可轮换的刷新令牌。

现有 `item`、`category`、`location` 增加 `household_id`，所有业务查询必须自动按当前用户家庭过滤，不能信任客户端任意传入的家庭 ID。

统一 API 建议：

```text
/api/v1/auth/*
/api/v1/items/*
/api/v1/categories/*
/api/v1/locations/*
/api/v1/dashboard/*
/api/v1/imports/*
```

PC 端重点承担：

- Excel/CSV 批量录入。
- 批量修改分类和位置。
- 数据清洗、重复项处理。
- 完整统计看板。
- 家庭成员、备份和系统配置。

小程序重点承担：

- 登录和家庭绑定。
- 快速录入物品。
- 拍照上传。
- 搜索、筛选和查看详情。
- 修改、移动和删除。
- 简化统计看板。
- 后续条码或二维码扫描。
