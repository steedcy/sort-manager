# ADR 0003：v1.5 采用原子批量录入协议与原生微信小程序客户端

- 状态：Accepted
- 日期：2026-07-21
- 关联：ADR 0002 的家庭账号、JWT 与 `/api/v1` 协议

## 背景

家庭物品首次建账通常一次录入几十件物品，逐条打开弹窗效率低；家庭成员也需要在手机旁随手查询和登记。项目部署在个人服务器，当前 React PWA 适合 PC，但微信内访问和手机快捷入口仍不足。

## 决策

1. 后端新增 `POST /api/v1/items/batch`，单次最多 100 行。请求带 `validateOnly`，响应逐行返回字段错误；提交模式先验证全部行，仅当全部有效时在一个事务内写入，避免半批数据。
2. 批量关联的分类和位置按家庭一次查询并建立映射，禁止逐行查询和跨家庭引用。日期使用严格 ISO `yyyy-MM-dd`，批量录入不沿用单条接口的静默日期回退。
3. PC 端提供独立“批量录入”工作台：支持粘贴 Excel/WPS 表格、导入 CSV、下载模板、逐格修正、服务端预检和一次提交。草稿只保存在当前浏览器 `sessionStorage`。
4. v1.5 小程序采用微信原生 JavaScript/WXML/WXSS，不引入跨端框架。基础版覆盖账号登录、会话刷新、统计总览、物品查询、单件快速录入和退出；复用 v1.4 JSON Token API。
5. 小程序 API 地址通过未提交的 `miniapp/config.js` 配置，仓库只提供 `config.example.js`。服务端必须使用受信任 HTTPS 域名并在微信公众平台配置 request 合法域名。
6. Web 与小程序保持同一家庭边界和角色模型，不增加新的公开端点，不把 Token 放入 URL、日志或代码。

## 方案取舍

- 未选择服务端上传并解析 Excel：会增加文件解析依赖、公式与宏风险；浏览器本地解析 CSV/粘贴文本更透明。
- 未选择部分成功：家庭建账更需要可预测性，原子提交能让用户修正后整批重试。
- 未选择 Taro/uni-app：基础版页面少，原生小程序依赖和构建成本最低；功能扩张后再评估跨端框架。

## 结果

- 批量接口和 UI 必须明确显示“预检”与“正式录入”两个状态。
- 小程序与 Web 的刷新令牌均为单次轮换，客户端必须串行刷新并保存新令牌。
- v1.5 不包含扫码识别、OCR、Excel `.xlsx` 解析、图片批量上传、离线写入或微信一键登录。

## 验证门禁

- 批量空请求、超过 100 行、字段错误、跨家庭引用、原子回滚和成功写入均有后端测试。
- Web 批量粘贴、预检、错误修正、成功提交和 375px 无横向溢出通过测试。
- 小程序脚本语法检查通过，登录刷新、401 重试与退出逻辑接受代码审查。
- Maven、前端 verify、Playwright、真实 MySQL 联调和 `/code-review` 均无 Critical/High 后才能提交。
