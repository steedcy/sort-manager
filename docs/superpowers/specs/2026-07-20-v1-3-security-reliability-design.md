# Sort Manager v1.3 安全与可靠性升级设计

**状态：** 已确认
**日期：** 2026-07-20
**基线：** v1.2.0 (`caf59a7`)

## 1. 问题陈述

v1.2 已形成可用的个人物品管理闭环，但前端依赖存在高危公告，后端 CORS 允许任意来源，数据库仍依赖 `ddl-auto=update`，且核心用户流程没有浏览器级回归测试。v1.3 的目标是消除这些上线前阻塞项，不扩展业务范围。

## 2. 目标用户与边界

目标用户仍是本地或家庭内网中的单用户。v1.3 不引入账号体系、多租户、云同步、导入导出或大规模 UI 重构；这些功能需要独立产品设计。现有未提交提示插图和桌面截图不属于本版本改动。

## 3. 方案比较

### 方案 A：最小安全闭环（推荐）

- 升级有公告的直接依赖，并分开验证 Vite 主版本升级。
- CORS 改为环境变量白名单，默认只允许本地前端。
- 引入 Flyway，兼容已有数据库和全新安装。
- 使用 Playwright 覆盖启动、列表分页和物品 CRUD。
- 优点：直接解决已知风险，范围清晰，可在一个版本内验证。
- 缺点：暂不提供登录鉴权。

### 方案 B：认证优先

- 先加入 Spring Security、登录页面和会话管理，再处理迁移与 E2E。
- 优点：更适合公网部署。
- 缺点：需要确定用户模型、密码恢复和部署方式，明显扩大版本范围。

### 方案 C：基础设施优先

- 先完成 Docker Compose、反向代理、HTTPS、备份和监控。
- 优点：部署体验完整。
- 缺点：不能优先解决当前依赖、迁移和回归测试缺口。

## 4. 推荐架构

### 4.1 依赖安全

先升级 Axios、React Router 等可兼容更新并运行现有门禁；Vite 与 React 插件作为单独批次升级。每批执行 `npm audit`、lint、生产构建和 Playwright。禁止直接使用未经验证的 `npm audit fix --force`。

### 4.2 CORS

新增 `APP_CORS_ALLOWED_ORIGINS`，默认 `http://localhost:5173`。后端解析逗号分隔白名单；测试验证允许配置来源并拒绝未知来源。生产环境必须显式配置，不再使用 `allowedOriginPatterns("*")`。

### 4.3 数据库迁移

引入 Flyway。`V1` 描述全新数据库基础结构；已有非空数据库通过 baseline 兼容。`V2` 增加分类名称唯一约束和物品筛选索引。Hibernate 改为 `validate`，`database/init.sql` 只保留可选示例数据职责。

### 4.4 E2E

Playwright 运行真实前端与后端。CI 使用 MySQL 服务容器，本地复用 `.env`。首批覆盖：页面启动及统计加载、物品新增/查询/删除、状态筛选与分页。测试创建的数据必须在用例结束后清理。

## 5. 错误与恢复策略

- 依赖升级失败时按批次回退，不混合锁文件变更。
- Flyway 迁移必须在副本/测试库先执行；检测到重复分类时明确失败，不自动删除业务数据。
- E2E 失败时保留截图、trace 和服务日志作为 CI artifact。
- CORS 配置为空或格式错误时使用安全的本地默认值并记录启动日志。

## 6. 成功标准

- `npm audit` 无 high/critical 漏洞，或对无法消除项有书面风险豁免。
- 未配置 CORS 时仅允许本地前端来源，未知来源的预检请求不获许可。
- 新数据库可从零迁移，当前 MySQL 数据库可 baseline 后升级且 6 条现有物品不丢失。
- 后端单元/集成测试、前端 lint/build 全部通过。
- 至少 3 条核心 Playwright 流程在本地和 CI 通过。
- `.env`、管理员凭据、测试产物不进入 Git。
