# Sort Manager 前端设计系统统一与全页面优化设计

日期：2026-07-30
状态：已确认，待实施

## 1. 背景与目标

Sort Manager 是供个人与家人共同使用的家庭物品管理应用，主要在 PC Web、手机浏览器与微信小程序场景下使用。Web 端已经覆盖总览、物品、批量录入、位置、分类、成员与家庭运营等核心流程，但现有视觉实现仍保留通用 SaaS 仪表盘特征，且样式治理存在以下问题：

- `frontend/src/index.css` 超过一千行，令牌、布局、组件、页面与响应式规则交织。
- 页面和组件中存在一百余处展示性内联样式。
- 页面直接使用大量十六进制颜色，浅色与深色规则重复。
- 按钮、卡片、标题、工具栏、状态标签、空状态和加载状态缺少统一组件契约。
- `frontend/src/App.css` 已不再使用，但仍保留 Vite 模板样式。
- 部分大页面同时承担数据、交互和大量展示结构，维护成本较高。

本轮目标是建立一套面向“家庭档案柜”场景的单一浅色设计系统，统一全部 Web 页面和共享组件，在不改变 API、权限和核心业务流程的前提下，提高可读性、触控体验、响应式质量、无障碍能力与长期可维护性。

## 2. 设计方案决策

### 方案一：在现有 CSS 上继续修补

改动最小，但无法消除单体样式、内联样式和页面间规范漂移，后续迭代仍会重复产生不一致。

### 方案二：设计令牌、通用组件与逐页重构

保留现有 React、React Router、Lucide 和业务组件体系，新增轻量的设计基础层与 UI 原语，逐页替换内联样式。改动边界清晰，能够显著改善质量且不引入新 UI 依赖。

### 方案三：引入完整组件库并重写

一致性提升快，但会带来依赖、视觉同质化、迁移量和回归风险，不符合家庭自用项目的当前规模。

采用方案二。

## 3. 视觉方向

### 3.1 主题

仅维护浅色主题，完全删除深色模式、主题切换按钮、主题上下文、深色令牌和主题分支代码。应用默认且始终呈现明亮、安静、适合日常长时间查看的界面。

### 3.2 视觉概念

视觉主题为“家庭档案柜”：

- 档案纸灰作为应用背景，白色作为内容表面。
- 墨色用于正文和关键数据。
- 竹青作为主操作色，表达整理、秩序与家庭生活。
- 琥珀色作为标签和提醒色，模拟真实收纳标签。
- 危险红仅用于删除、过期和失败状态。

标志性元素为“收纳标签条”。它用于页面标题、分组标题和物品元信息，以窄色条、标签切口或轻量边框表达内容归档关系。该元素只服务于信息分组，不作为无意义装饰。

### 3.3 色彩令牌

最终实现须以语义令牌为准，页面不得直接引用品牌色值：

- `--color-canvas`：应用背景
- `--color-surface`、`--color-surface-muted`：一级与次级表面
- `--color-ink`、`--color-ink-secondary`、`--color-ink-muted`：三级文字
- `--color-primary`、`--color-primary-hover`、`--color-on-primary`：主操作
- `--color-accent`、`--color-accent-soft`：标签与提示
- `--color-success`、`--color-warning`、`--color-danger`：语义状态
- `--color-border`、`--color-border-strong`、`--color-focus`：边界与焦点

候选主色以竹青 `#2F6B57` 为基准，实施时必须通过 WCAG 对比度校验。分类自定义颜色属于业务数据，可通过 CSS 自定义属性传入，但必须同时显示文字或图标，不能只用颜色表达含义。

### 3.4 字体与数字

- 展示标题：`"Songti SC", "STSong", "Noto Serif CJK SC", serif`
- 正文与控件：`-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif`
- 数据、价格、数量和时间使用 `font-variant-numeric: tabular-nums`

字体尺寸采用有限的语义层级，不允许页面自行定义相近但不同的字号：

- 展示标题：32–44px，响应式缩放
- 页面标题：24–28px
- 区块标题：18–20px
- 正文：16px
- 辅助文字：14px
- 标签文字：12px，禁止更小的正文信息

正文行高不低于 1.5。

## 4. 设计令牌与样式架构

样式按职责拆分：

- `src/styles/tokens.css`：颜色、字体、间距、圆角、阴影、层级和动效令牌
- `src/styles/base.css`：重置、正文、链接、焦点、滚动条和无障碍辅助类
- `src/styles/layout.css`：应用外壳、侧栏、页面容器、网格和响应式结构
- `src/styles/components.css`：按钮、输入框、卡片、标签、弹窗、空状态、骨架屏等共享组件
- `src/styles/pages.css`：只保留无法归入共享层的页面特有组合规则
- `src/index.css`：仅负责导入上述样式

删除未使用的 `src/App.css`。清除展示性 JSX 内联样式；动态分类色、进度比例等运行时数据仅通过命名清晰的 CSS 自定义属性传递。

令牌体系采用 4/8px 节奏：

- 间距：4、8、12、16、24、32、48、64
- 圆角：8、12、16
- 阴影：卡片、浮层、弹窗三档
- 层级：基础、粘性标题、导航、浮动操作、遮罩、弹窗
- 动效：150–220ms，统一缓动，仅使用 `opacity` 和 `transform`

## 5. 共享组件规范

新增或重构以下共享 UI 组件：

- `PageHeader`：图标、标题、副标题、主要操作和可选标签条
- `Button`：primary、secondary、ghost、danger、icon 变体及统一加载状态
- `Card`：default、interactive、muted、danger 变体
- `FormField`：标签、必填标记、帮助文字、控件和字段错误
- `StatusBadge`：success、warning、danger、neutral，必须包含文本
- `EmptyState`：图标、标题、说明和可选主要操作
- `Modal`：焦点管理、关闭、标题、正文与操作区
- `Skeleton`：卡片、文本、列表三类骨架
- `Toolbar`：搜索、筛选、次要操作和移动端折行
- `Pagination`：摘要、页码操作和每页数量

组件须支持 `className` 扩展，但页面不得通过内联样式重写组件基础尺寸。图标统一使用 Lucide，装饰图标标记 `aria-hidden`，图标按钮提供明确的无障碍名称。

## 6. 页面设计

### 6.1 登录页

保留双栏叙事结构，将现有深色视觉改为明亮的档案柜封面。左侧呈现家庭收纳索引与隐私提示，右侧为聚焦的登录表单。移动端优先显示表单，再显示简化品牌信息。

### 6.2 应用外壳与导航

桌面端使用稳定侧栏，内容区最大宽度 1280px。侧栏明确区分主导航、家庭管理和账户操作。移动端保持最多五个顶层入口的底部导航，批量录入与家庭运营通过相关主页面的明确入口访问。所有固定区域遵守安全区并为内容预留空间。

### 6.3 收纳总览

按“家庭库存摘要、临期提醒、最近录入、分类分布”的优先级组织。统计卡统一数字排版；预警使用文字、图标和语义边界；分类数据提供可读标签，不只依赖彩色条。

### 6.4 物品管理

统一页面标题、搜索筛选工具栏、物品卡、状态标签、分页和批量操作浮层。卡片必须保持名称、位置、分类、数量、日期和操作的稳定层级。选中状态不得通过改变边框宽度造成布局抖动。

### 6.5 批量录入

保持“导入/粘贴、预检、修正、提交”流程，强化步骤说明、错误摘要和底部操作区。移动端字段改为单列或合理双列，避免固定浮层遮挡最后一行内容。

### 6.6 收纳位置与分类

位置树节点和分类卡使用同一管理卡片语言。编辑、删除按钮尺寸与间距统一；层级缩进、物品数量和描述有稳定信息位置。分类颜色选择器同时显示颜色名称或代码。

### 6.7 家庭成员

桌面表格和移动卡片共享相同状态、角色与操作语义。创建成员表单使用 `FormField`，密码要求作为持续可见的帮助信息。停用、撤销会话等危险操作与普通信息分隔。

### 6.8 家庭运营

保留操作记录与回收站双区域，统一状态摘要、筛选、时间线、回收站卡片、分页和确认弹窗。备份异常、恢复和永久删除均须有明确后果说明。

## 7. 响应式与交互

验证宽度为 375、768、1024 和 1440px，并覆盖手机横屏：

- 不产生页面级横向滚动。
- 触控目标至少 44×44px，相邻触控目标间距至少 8px。
- 输入控件移动端字号至少 16px，避免 iOS 自动缩放。
- 页面内容不被粘性标题、底部导航或浮动操作区遮挡。
- 长标题和家庭名称优先换行，必要截断时提供完整信息。
- 卡片悬停只用于增强，不承载唯一功能。

所有交互状态统一包含默认、悬停、按下、键盘聚焦、禁用和加载状态。动效服务于状态变化，并支持 `prefers-reduced-motion`。

## 8. 无障碍与反馈

- 页面保持唯一 `h1`，区块按顺序使用 `h2`、`h3`。
- 保留跳到主要内容链接和路由切换后的主内容聚焦。
- 所有表单字段使用可见 `label` 和正确关联。
- 字段错误显示在相关控件附近，多错误场景提供顶部摘要。
- 状态变化与表单错误使用合适的 `aria-live` 或 `role="alert"`。
- 弹窗支持 Escape、明确关闭按钮、焦点圈定与关闭后焦点恢复。
- 删除和永久删除继续要求确认，并与普通操作视觉分隔。
- 空状态说明当前原因和下一步；加载超过 300ms 时显示骨架或进度。
- 正文与背景对比度至少 4.5:1，大文字至少 3:1。

## 9. 测试与验收

保持现有业务测试，并增加或扩展 Playwright 验证：

- 全部页面具有正确标题和主要结构。
- 不再出现主题切换控件和深色主题分支。
- 关键按钮与输入控件满足最小触控尺寸。
- 375、768、1024、1440px 下无页面级横向溢出。
- 移动底部导航不超过五项且不遮挡内容。
- 登录、物品录入、批量录入、筛选、成员管理、回收站流程不回归。
- 键盘焦点可见，弹窗焦点和关闭行为正确。
- `prefers-reduced-motion` 下动效被关闭或显著缩短。

完成标准：

1. 删除深色主题相关实现和未使用样式。
2. 展示性内联样式清零；动态业务值仅使用 CSS 自定义属性。
3. 除令牌文件和分类业务色板外，不存在页面硬编码颜色。
4. 所有页面使用统一标题、按钮、表单、卡片、状态和反馈规范。
5. 前端单元测试、lint、生产构建和全部桌面/移动端 E2E 通过。
6. 浏览器完成浅色视觉、响应式、键盘、动态文字与降低动效检查。
7. 最终代码审查无阻塞问题。

## 10. 非目标

- 不修改后端 API、数据库结构、权限模型和认证流程。
- 不引入新的 UI 组件库、图表库或动画库。
- 不重写微信小程序视觉体系；本轮仅处理 React Web 前端。
- 不新增与样式统一无关的业务功能。
